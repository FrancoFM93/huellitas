# Huellitas: recovery audit and next release plan

Audit date: 21 October 2026. This document describes the repository baseline and the bounded recovery patch prepared from it. It is not a production certification or evidence that the hosted Supabase project has these changes.

## 1. Where development stopped

The continuation point is **`dev` at `b73a34e160519ecf49ce871afdf88d1ceb0ea00d`**, dated 28 April 2026. It is **17 commits ahead of `main`**, with no commits behind. `main` is at `ec3971fa7a5b59fc987cd4a376f6cb2aeb2e775d`, dated 23 April 2026. Starting from `main` alone would omit the newer adoption workflow, messaging, account settings, and other work.

- [Baseline comparison: main to dev](https://github.com/FrancoFM93/huellitas/compare/ec3971fa7a5b59fc987cd4a376f6cb2aeb2e775d...b73a34e160519ecf49ce871afdf88d1ceb0ea00d)
- [Last baseline commit](https://github.com/FrancoFM93/huellitas/commit/b73a34e160519ecf49ce871afdf88d1ceb0ea00d)
- [Original foundation design](superpowers/specs/2026-04-20-fundaciones-ongs-design.md)
- [Original implementation plan](superpowers/plans/2026-04-21-fundaciones-ongs.md)

The original plan contains unchecked steps for work that is already present. Its checkboxes are not reliable completion evidence. Use the code, migration history, and verified acceptance criteria below when resuming.

The existing stack remains Expo 55, React Native, Expo Router, TypeScript, Supabase, TanStack Query, Zustand, and i18next. No framework rewrite is needed to make progress. The project has substantial screens and data structures, but important permissions, state transitions, and deployment setup still prevent treating it as a finished public app.

## 2. What exists, and what is unfinished

"Present" in this table means implemented in source. It does not mean the workflow was verified on a physical device against the hosted database.

## 3. Confirmed baseline defects

Priorities: **P0** blocks exposing the affected function to public users; **P1** blocks a dependable beta; **P2** is an important correctness or completeness issue to schedule after those blockers. Priorities describe impact in the shipped design, not proof that a live system was exploited.

### A. Authorization and trust boundaries

**P0: users could edit privileged profile fields.** The owner UPDATE policy restricts rows but not columns. The later migration adds `role` and `verified` without protecting those columns. With the expected client grants, an account could promote itself to admin or verified foundation, affecting broadcast authorization. The recovery migration restricts columns and owner policies. Existing deployed grants and any additional policies still need inspection.

Evidence: [baseline profile policies](https://github.com/FrancoFM93/huellitas/blob/b73a34e160519ecf49ce871afdf88d1ceb0ea00d/supabase/schema.sql#L190-L193), [role and verification additions](https://github.com/FrancoFM93/huellitas/blob/b73a34e160519ecf49ce871afdf88d1ceb0ea00d/supabase/migrations/2026_04_21_01_geo_and_roles.sql#L5-L10).

**P0: public-content inserts did not bind authors to the session.** Missing reports, sightings, alerts, responses, campaigns, and adoption posts had policies that generally checked only whether the caller was authenticated. A supplied author ID could belong to another account. Missing reports also lacked an ownership check on the pet. The patch binds these inserts to the caller's active profile and, for missing reports, its owned pet.

Evidence: [baseline content policies](https://github.com/FrancoFM93/huellitas/blob/b73a34e160519ecf49ce871afdf88d1ceb0ea00d/supabase/schema.sql#L215-L249), adoption policies later in the same schema.

**P0: donation balances were directly writable without payment confirmation.** Both money screens inserted a donation and then called a separate amount-increment RPC. Those `SECURITY DEFINER` routines had no caller check or explicit client execution revocation. A database write was presented as a successful donation, and RPC errors were ignored. The client also passed `auth.users.id` where `donations.donor_id` references `profiles.id`, which normally causes a foreign-key failure. Simply fixing that ID would have made the unverified money workflow more usable without making it trustworthy.

Evidence: [baseline fund mutation](https://github.com/FrancoFM93/huellitas/blob/b73a34e160519ecf49ce871afdf88d1ceb0ea00d/app/%28tabs%29/fund.tsx#L170-L205), [campaign mutation](https://github.com/FrancoFM93/huellitas/blob/b73a34e160519ecf49ce871afdf88d1ceb0ea00d/app/fundraising/%5Bid%5D.tsx#L71-L89), [balance routines](https://github.com/FrancoFM93/huellitas/blob/b73a34e160519ecf49ce871afdf88d1ceb0ea00d/supabase/schema.sql#L260-L280).

The patch removes donation actions, modals, success messages, raised totals, and donation histories from the client. Campaign browsing, descriptions, creation, and targets remain. Database permissions disable client donation/balance writes. No payment gateway, collection, withdrawal, or refund workflow has been added. Existing records are preserved and require reconciliation before any future money feature uses them.

**P1: application, follow-up, message, and notification permissions were broader than the UI implied.** Applicants could supply approval fields on INSERT or reassign application data during withdrawal. Adopters could update session verification fields. Thread participants could alter message content rather than only mark messages read. Notification recipients could insert or modify notification contents and metadata. The deletion queue lacked RLS. The patch narrows these permissions; see migration 12 for exact grants and policies.

Evidence: [application policies](https://github.com/FrancoFM93/huellitas/blob/b73a34e160519ecf49ce871afdf88d1ceb0ea00d/supabase/migrations/2026_04_21_06_adoption_applications.sql#L27-L36), [monitoring policy](https://github.com/FrancoFM93/huellitas/blob/b73a34e160519ecf49ce871afdf88d1ceb0ea00d/supabase/migrations/2026_04_21_07_contracts_and_monitoring.sql#L49-L55), [message policy](https://github.com/FrancoFM93/huellitas/blob/b73a34e160519ecf49ce871afdf88d1ceb0ea00d/supabase/migrations/2026_04_21_11_vet_messages.sql#L61-L69), [deletion queue](https://github.com/FrancoFM93/huellitas/blob/b73a34e160519ecf49ce871afdf88d1ceb0ea00d/supabase/migrations/2026_04_21_10_account_deletion.sql#L8-L13).

**P1: the push sender trusted caller-supplied notification contents.** The function used a service-role client after accepting an arbitrary notification record. The patch requires a webhook-only secret and loads the notification by ID from the database. This must be deployed together with its secret and matching webhook header. It does not establish delivery retry/idempotency or complete Expo receipt processing.

Evidence: [baseline sender](https://github.com/FrancoFM93/huellitas/blob/b73a34e160519ecf49ce871afdf88d1ceb0ea00d/supabase/functions/send-push/index.ts#L12-L45), [current handler](../supabase/functions/send-push/handler.ts).

### B. Account/session reliability

**P1: a fresh database could create an auth account without its required application profile.** Registration passes metadata to Supabase Auth, but no repository trigger creates `public.profiles`; onboarding expects that row to already exist. Migration 13 adds server-side profile bootstrap and backfills missing rows without overwriting existing profiles or trusting metadata for privileged fields. The hosted project might already contain an out-of-repository trigger, which must be checked before applying this migration.

**P1: auth callbacks and in-flight requests could leave stale account state.** The baseline awaited another Supabase operation inside `onAuthStateChange`, loaded account data without a generation guard, and did not clear the query cache and notification rows as one account boundary. The patch separates profile fetching from the auth callback, adds request-generation guards and explicit error states, clears user caches, and gates routes and notification navigation. A successful type check is insufficient to prove all native OAuth/cold-start sequences.

Evidence: [baseline auth callback](https://github.com/FrancoFM93/huellitas/blob/b73a34e160519ecf49ce871afdf88d1ceb0ea00d/app/_layout.tsx#L31-L61), [baseline auth store](https://github.com/FrancoFM93/huellitas/blob/b73a34e160519ecf49ce871afdf88d1ceb0ea00d/store/authStore.ts#L36-L79), [current lifecycle helper](../lib/authState.ts).

**P1, open: account deletion promises more than the implementation performs.** The RPC anonymizes some profile fields and queues work, while the UI promises the user can never sign in again. No worker processes the queue, removes stored files, or cleans subsidiary clinic/vet/foundation contacts. Deleting `auth.users` naively would cascade through profiles and adoption records, conflicting with the promise to preserve contracts. The patch protects the queue and rejects deleted profiles in the app, but client rejection is not equivalent to revoking credentials or securing every remaining database policy. A synthetic local SQL check after migrations 12 and 13 reproduced a deleted poster still calling `fn_approve_application` and `fn_verify_session` successfully as an authenticated user. This is a demonstrated residual backend permission gap; the hosted project was not tested. Define and implement the full retention/deletion workflow before public release.

Evidence: [deletion RPC and comments](https://github.com/FrancoFM93/huellitas/blob/b73a34e160519ecf49ce871afdf88d1ceb0ea00d/supabase/migrations/2026_04_21_10_account_deletion.sql), [baseline user-facing promises](https://github.com/FrancoFM93/huellitas/blob/b73a34e160519ecf49ce871afdf88d1ceb0ea00d/locales/en.json#L180-L194).

**P2, open: password recovery is a dead control.** The login screen renders a forgot-password `TouchableOpacity` without an `onPress`. Complete request, email deep link, password-update, and expired-link states before claiming recovery support.

Evidence: [baseline login](https://github.com/FrancoFM93/huellitas/blob/b73a34e160519ecf49ce871afdf88d1ceb0ea00d/app/%28auth%29/login.tsx#L131-L133).

### C. Privacy that remains unresolved

**P1, open: publicly readable rows combine public and private fields.** `profiles` includes push tokens, contact details, identity links, and precise location under public row-level reads; `pets` publicly exposes microchip and medical notes. Narrower SELECT projections in some screens do not close this API-level exposure. Define an explicit public projection and protected private data access, and test anonymous and unrelated authenticated access to each field.

**P1, open: follow-up photos use public storage.** `monitoring/[sessionId]` uploads through the shared `photos` bucket. That bucket is public and its SELECT policy permits listing. Database row privacy does not protect those image URLs. Move private follow-up media into private storage with contract-participant authorization and expiring access; plan how existing public media is migrated and invalidated.

Evidence: [public pet policy](https://github.com/FrancoFM93/huellitas/blob/b73a34e160519ecf49ce871afdf88d1ceb0ea00d/supabase/schema.sql#L208-L213), [storage policies](https://github.com/FrancoFM93/huellitas/blob/b73a34e160519ecf49ce871afdf88d1ceb0ea00d/supabase/storage.sql#L5-L16), [follow-up upload](https://github.com/FrancoFM93/huellitas/blob/b73a34e160519ecf49ce871afdf88d1ceb0ea00d/app/monitoring/%5BsessionId%5D.tsx#L45-L54).

The existing settings links point to `https://huellitas.app/terms` and `/privacy`. A public lookup returned pages with a `lassie-forever` title, but no extractable body. That is not evidence of a 404 or proof of ownership. Confirm that these are the intended, maintained policies for this app before shipping them.

### D. Core workflow correctness

**P1, open: missing-pet transitions are not atomic.** Creating a report first marks the pet missing and then inserts the report; failure leaves a missing pet without a report. Marking a pet found performs two independent updates, ignores both errors, and then announces success. It also leaves related feed/map caches stale. Use a server transaction for each transition and return authoritative state.

**P1, open: community response and sighting counts are incorrect for ordinary participants.** The client inserts a child row and then tries to update its parent's count. RLS permits only the parent owner to update that parent, so another person's legitimate contribution does not update the count. Concurrent client read-modify-write operations can also lose increments. Derive counts from rows or maintain them transactionally on the server.

Evidence: [missing creation](https://github.com/FrancoFM93/huellitas/blob/b73a34e160519ecf49ce871afdf88d1ceb0ea00d/app/missing/new/%5BpetId%5D.tsx#L90-L109), [found action](https://github.com/FrancoFM93/huellitas/blob/b73a34e160519ecf49ce871afdf88d1ceb0ea00d/app/pets/%5Bid%5D.tsx#L30-L43), [sighting count](https://github.com/FrancoFM93/huellitas/blob/b73a34e160519ecf49ce871afdf88d1ceb0ea00d/app/missing/%5Bid%5D.tsx#L72-L98), [response count](https://github.com/FrancoFM93/huellitas/blob/b73a34e160519ecf49ce871afdf88d1ceb0ea00d/app/alerts/%5Bid%5D.tsx#L68-L88).

**P1, open: adoption approval does not serialize the shared post decision.** The approval routine locks the application row but reads its shared post without `FOR UPDATE`. Two approvals on different applications can pass the availability check concurrently and contend while changing the same post and rejecting other applications. The transaction is not a verified single-winner workflow; deadlocks or inconsistent outcomes must be tested. Lock the post before deciding, keep a consistent lock order, and add the appropriate uniqueness/invariant constraints. Do not claim a reproduced duplicate contract without a concurrent test.

**P1/P2, open: follow-up lifecycle does not reach completion.** The schema supports active/completed/cancelled contracts, but the repository has no contract completion/cancellation routine. Missed-session housekeeping is invoked by loading the poster panel; the planned scheduled reminders and missed notifications are absent. The current policy differs from the original plan: seven days and no evidence, rather than three days with notifications. The UI also stops posters from reopening completed sessions through the contract list. These are unfinished product decisions/workflows, not merely styling.

Evidence: [approval and verification routines](https://github.com/FrancoFM93/huellitas/blob/b73a34e160519ecf49ce871afdf88d1ceb0ea00d/supabase/migrations/2026_04_21_07_contracts_and_monitoring.sql#L57-L116), [housekeeping](https://github.com/FrancoFM93/huellitas/blob/b73a34e160519ecf49ce871afdf88d1ceb0ea00d/supabase/migrations/2026_04_21_08_adoption_notifications.sql#L140-L153).

**P1, open: geographic notifications can target the wrong place or no place.** Only foundation onboarding writes country/region/city, while alerts copy the author's profile fields rather than resolve the incident location. A normal account's fields can remain null; a traveling foundation account can target its home city. The legacy high-severity trigger also targets all vets/clinics, not "nearby" professionals as the success message says. Confirm intended recipients and use incident geography before trusting emergency coverage.

**P2: public profile to professional detail used incompatible IDs.** Public profiles linked with `profiles.id`, while vet/clinic detail queries expect `vet_profiles.id`/`clinic_profiles.id`. The patch loads the actual subprofile IDs and adds retry, unavailable, and back states. Directory search remains separate: its left-joined profile filter retains nonmatching parent rows. Use `!inner` when the intent is to restrict parent rows, consistent with [Supabase's join documentation](https://supabase.com/docs/guides/database/joins-and-nesting).

Evidence: [baseline profile link](https://github.com/FrancoFM93/huellitas/blob/b73a34e160519ecf49ce871afdf88d1ceb0ea00d/app/profile/%5Bid%5D.tsx#L98-L105), [baseline directory queries](https://github.com/FrancoFM93/huellitas/blob/b73a34e160519ecf49ce871afdf88d1ceb0ea00d/app/%28tabs%29/search.tsx#L17-L41).

**P2, open: missing/error states frequently look like loading or empty data.** Many query functions discard Supabase's `error`, return null/empty data, and render a spinner whenever data is missing. An offline connection, missing migration, inaccessible row, and genuinely empty result become indistinguishable. The patch fixes this in the fund and public-profile screens and auth entry path; the rest of the screens still require the same treatment.

### E. Media, notifications, and distribution

The patch replaces Blob-based native photo uploads with a base64-to-ArrayBuffer path, adds input/MIME checks, and handles picker errors. This follows the supported upload pattern, but camera/gallery permissions, actual picked formats, and resulting images still need physical-device verification. See [Supabase's React Native upload example](https://supabase.com/blog/react-native-storage).

The baseline sighting trigger emitted `report_id`, which notification routing ignored. The patch accepts the relevant route aliases, validates IDs, and delays cold-start navigation until authentication/profile/navigation are ready. Android notification channel setup and the Expo notifications plugin are included.

Remaining distribution requirements include a chosen iOS bundle identifier, appropriate native location/photo permission configuration, Android map credentials for standalone builds, EAS development/preview builds, FCM/APNs setup, Supabase webhook authentication, Realtime publication configuration, and OAuth/email callback allowlists. The repository cannot prove the current settings of these hosted services. A single push token on a public profile also does not provide a safe multi-device token lifecycle.

### F. Dependency maintenance

The [deduplicated dependency snapshot](dependency-audit-2026-10-21.json) records two Yarn 1.22.22 registry scans around a bounded lockfile refresh. `shell-quote` moved from 1.8.3 to 1.12.0 within its parent's existing `^1.6.1` requirement. That removes its reported critical and high advisories without adding a direct dependency or forcing an SDK upgrade. These scans both include the recovery patch's test tools and React DOM compatibility pin; they are not an untouched-baseline comparison.

The final scan contains **49 distinct GHSA URLs across 17 packages: 35 high, 13 moderate and 1 low, with no critical registry advisory remaining**. Yarn reports 296 repeated advisory/path entries; that is not 296 distinct vulnerabilities or demonstrated app exploits. Much of the graph is Expo/Metro/build/development tooling, while several navigation and network dependency chains need runtime review. The JSON includes installed versions, paths, upstream advisory links and exposure notes.

This remains release maintenance work. The separate `shell-quote` update does not rewrite the older parser embedded inside the standalone DevTools bundle. Some installed dependency lines have no fixed version recorded. Plan a supported Expo/React Native/toolchain upgrade and compatibility review before launch; neither a successful bundle nor a registry scan establishes production safety.

## 5. Milestones for finishing the existing product

### Milestone 1: reproducible, protected private beta

Apply the recovery branch to a disposable/local or staging environment first. Document the exact schema/migration order and configure the authenticated webhook together with the new sender. Review private profile/media access and account-deletion behavior before inviting users with real personal data.

Acceptance criteria:

- A new database can be created from documented repository files without missing schema dependencies.
- Owner, applicant, vet, foundation, and unrelated-user test identities exercise the intended policies. Nonowners cannot impersonate authors, self-verify, alter other messages, or modify financial totals.
- New email and Google accounts have base profiles. Email-confirmed professional accounts can reach and finish their appropriate onboarding. Restart, sign-out, account switch, and slow failed profile requests do not leak previous-user state.
- The donation interface clearly states that donations are unavailable. No client action claims that funds were collected.
- Authorized webhook requests work; requests without the dedicated credential fail; notification content comes from the database.
- Errors produce recovery actions rather than indefinite loading. Android/iOS preview builds are tested on physical devices for the chosen initial platform scope.

### Milestone 2: dependable lost-pet and community loop

Finish the already-present flows: pet registration, missing report, community sighting, found transition, alert response, alert resolution, directory search/contact. Use server transactions and counts, and make geographical targeting match the incident.

Acceptance criteria:

- A failed request cannot leave `pets.is_missing` inconsistent with active reports. Retried creation does not create duplicate active reports.
- Two people reporting sightings/responses concurrently produce accurate counts; neither needs ownership of the parent record.
- Found/resolved state is reflected in the detail, feed, map, and profile without restarting the app.
- Two-city tests prove correct notification recipients; absent location and denied GPS permissions have clear behavior.
- All directory entry paths open the correct professional, and searching an unmatched name produces an empty result.

### Milestone 3: complete adoption and follow-up loop

Finish application status management, serialized approval, contract completion/cancellation, evidence privacy, and scheduled reminders using the original design as the scope reference. Specify whether the current "contract" is merely an operational follow-up record or a separately implemented agreement flow.

Acceptance criteria:

- An applicant cannot accidentally submit repeated pending applications, can withdraw, and sees the real status. Posters can reject without first approving someone else.
- Concurrent approval attempts result in one committed adoption and a clear conflict for the other caller; one post has the intended number of active contracts.
- Evidence uploads are available only to contract participants. The adopter cannot self-verify or alter the schedule.
- Scheduled reminders run without a person opening the app. Missed/completed/cancelled behavior is defined, visible to both parties, and testable.
- Completed sessions remain reviewable, and contracts can reach the final states already represented in the UI.

### Milestone 4: close operational and release gaps

Complete foundation profile editing/verification procedures, the password recovery flow, account deletion processing, remaining error states and translations, and the native distribution checks. Confirm geography/currency choices: the current map defaults to Buenos Aires and campaign amounts use ARS, while foundation onboarding defaults to Chile. Preserve the original global-ready intent, but choose explicit defaults for the first audience.

Before any future fundraising activation, design server-confirmed payments, reconciliation, recipient ownership, and failure handling. This is deliberately separate from making the current community/adoption functionality reliable. The original foundation specification explicitly excluded payment processing; this recovery work does not invent it as an already-completed capability.

## 6. Verification and limits

The integrated recovery checkout was verified locally with Node 24.19.0 and Yarn 1.22.22:

| Check | Result | What it establishes |
| --- | --- | --- |
| `corepack yarn install --offline --frozen-lockfile --ignore-scripts --non-interactive` | Passed from the populated cache | Manifest and lockfile resolve without a lock update. |
| `corepack yarn verify` | Passed | Runs TypeScript followed by the full regression command. |
| `corepack yarn test` (included above) | 41 tests passed, 0 failed, 0 skipped/cancelled | Named auth, OAuth, actual SQL policy/grant/trigger/RPC, bootstrap, notification, photo-payload and push-webhook checks; Node's count includes parent tests. |
| `expo export --platform android --platform ios --max-workers 2` | Passed for both platforms | JavaScript/Hermes exports, using an explicitly nonfunctional Supabase URL/key and offline mode. No APK/IPA or device interaction. |
| `expo config --type public --json` | Passed | App configuration resolves, including the notifications plugin. |
| `expo install --check` in offline mode | Reported dependencies up to date | Compatibility check using local Expo metadata only; not a current registry-security assessment. |
| `git diff --check` | Passed | No introduced whitespace errors. |
| Yarn registry audit | Completed with remaining findings | 49 distinct advisories remain; see section F and the JSON evidence, not a clean security result. |

The SQL harness executes the checked-in base schema and all 13 migrations in PGlite with synthetic Auth/API roles, replacing UUID generation and omitting unused native extensions. It verifies allowed paths as well as rejected privilege/ownership changes. It does not exercise Supabase Storage policies or prove the permissions, migration history, data, or configuration of the hosted project.

The test process uses `--no-wasm-code-gc` after an intermittent V8 fatal assertion matching [Node issue 66366](https://github.com/nodejs/node/issues/66366). Complete runs pass with this temporary test-only workaround; fixture cleanup and assertions remain enabled. See the README for its scope and removal condition. The [CI workflow](../.github/workflows/ci.yml) repeats installation, types, tests and native exports without credentials or deployment permissions; its actual remote execution status is reported by GitHub.

**Delivery status on 21 October:** the GitHub integration rejected the attempted tree publication with HTTP 403, `Resource not accessible by integration`. The work is preserved on the local `audit/resume-huellitas` branch and in the downloadable recovery package. No remote branch or pull request was created, and GitHub Actions has not run this patch. Publishing requires an authorized GitHub connection with the necessary repository write permissions.

Not performed as part of this audit: applying migrations to the hosted project, accessing real user data, publishing an Edge Function, deploying a mobile build, testing actual Google/email provider configuration, or verifying flows on a physical device. No claim is made that fundraising, privacy, account deletion, or overall security is fully solved.

The immediate outcome is a recovered development baseline, a bounded first patch, and a concrete path to finish the existing app. Keep remaining work tied to the acceptance criteria above instead of expanding the feature list.
